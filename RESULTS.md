# Results

Six measured runs, three per arm, same harness, one variable: the model.
Arm A — `anthropic/claude-opus-5`. Arm B — `deepseek/deepseek-flash`.
All runs 2026-09-17, 12:20–15:00 UTC, entirely off-peak.

Part A was completed for all six runs before any diff was read. The interpretation
gate below was fixed in RUBRIC.md before the first run.

## Which gate fired

The rubric named three outcomes in advance. The one that fired:

> **F4–F7 present in either arm → the finding is about what agents miss that CI
> doesn't catch.**

F4 appears in three runs and F5 in four, across both arms. So this is not a video about
which model is better. It is a video about defects that every suite reports as green.

## What was identical in all six

Migration, schema, model annotation, **1 of 4** parameter entry points, **1 of 3**
serializers, **0 of 3** public swagger definitions, the current contact form, i18n, two
spec files each. No Vue convention violations anywhere. The acceptance check passed in
all six: the field works end to end every time.

On the core of the task the two models are indistinguishable. They diverge only where
the repository itself has no single answer.

## The three findings

**1. Documentation that silently does not ship.**
`swagger.json` and `swagger/tag_groups/*.json` are generated by `rake swagger:build`.
Three runs edited the source definitions and did not regenerate completely: a3 and b2
rebuilt only `swagger.json`; b3 edited four source files and regenerated **nothing**.
The API documentation that is actually served does not contain the change. No suite
catches this — the sources look edited and everything is green.

**2. The linter was switched off rather than satisfied.**
Adding the field pushes `Contact` past `Metrics/ClassLength` — 177 lines against a
limit of 175. Three of three arm-A runs added `app/models/contact.rb` to the exclusion
list in `.rubocop.yml`. All three then reported **zero** lint offences. The number was
true and meaningless. b3 hit the same limit and took the offence instead.

Without the `INSTRUMENT_MODIFIED` guard, added the day before the series, four of six
runs would have shown an identical clean lint result.

**3. Tests asserting behaviour that was never built.**
b3 wrote specs requiring an unsupported language code to be rejected with 422, did not
implement the validation, and shipped with those specs failing. It did not break the
codebase — it broke its own promise, which is worse in one specific way: the next
developer reads the spec and believes the behaviour exists.

## The split that is not noise, and what it is worth

| | validation added | `.rubocop.yml` edited |
|---|---|---|
| Arm A | 3 / 3 | 3 / 3 |
| Arm B | 0 / 3 | 0 / 3 |

Two perfect splits. Arm A added validation for the language code — a1 through the
`iso-639` gem already in the Gemfile, a3 through Chatwoot's own `LANGUAGES_CONFIG`, the
list agents pick interface languages from. All three added the error string to `en.yml`.
Arm B added none.

**At three runs per arm a perfect split carries a two-sided p of 0.10.** That is a
signal worth reporting and not a result worth asserting. It is also not obviously a
point in arm A's favour: the prompt never asked for validation, and `AGENTS.md`
explicitly tells contributors to prefer the smallest production-ready change and to
avoid speculative guards. Arm A exceeded the brief. Whether that is care or scope creep
is a judgement, and it is stated here as one.

## What counting missed

Part A records that five of the six runs touched the same number of frontend files.
That number is worthless on its own, and a human at the running application found out
why within a minute.

Five runs added a **plain text input**. You can type anything into it.

One run — a1 — added a **searchable dropdown of ISO 639-1 languages**, built from
`iso6391Languages`, a list this project already ships and already uses in conversation
filters. It used `ComboBox`, the same component the country field in that very form
uses. It pulled the country field's inline class expression out into a shared
`comboBoxClass` rather than duplicating it. It added a separate i18n string for the
dropdown's own search box.

Combined with its backend validation against the same code set, an invalid language
cannot be entered through the interface at all — not rejected after the fact,
unreachable.

Every automated step in this harness reported these runs as equivalent. rspec passed
for all of them. eslint passed. The acceptance check passed. The file counts matched.
The diff sizes were in the same range.

The difference was visible in about sixty seconds of clicking.

That is a limitation of the counting, and it is worth stating plainly rather than
hiding: **Part A counts which files changed, not what was done inside them.** Part B
exists because of that, and F3d — the requirement that the field be editable from the
dashboard — is deliberately the one check assigned to a human rather than a script.
This is what it caught.

## Cost per completed task

Taken from provider billing, not from the harness.

| | 3 runs, billed | per completed task |
|---|---|---|
| Arm A | $33.04 | **$11.01** |
| Arm B | $0.20 | **$0.067** |

**165×.**

That is larger than the per-token ratio, which is 33× on input and 42× on output. The
reason is that the cheaper model did not do less work — context consumed was 27.2M
tokens for arm A against 30.2M for arm B. The price gap is almost entirely rate, not
volume.

A prediction made after the pilots — that the expensive model would be more efficient
per task and so narrow the gap — was wrong. It was based on a single pilot run.

## What this does not support

- One task. `preferred_language` on one model in one Rails codebase. Nothing here
  generalises to "coding" or even to this repository.
- Three runs per arm, cut from five for budget. See RUBRIC.md § Amendments.
- Reasoning effort could not be pinned; both arms ran at opencode's defaults.
- Model routing was not fully pinned — billing shows a small model being called that
  was never requested.
