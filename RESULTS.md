# Results

Six measured runs, three per arm, same harness, one variable: the model.
Arm A — `anthropic/claude-opus-5`. Arm B — `deepseek/deepseek-flash`.
All runs 2026-09-17, 12:20–15:00 UTC, entirely off-peak.

Part A was completed for all six runs before any diff was read. The interpretation
gate below was fixed in RUBRIC.md before the first run.

## Which gate fired

The rubric named three outcomes in advance. The one that fired:

> **F4–F7 present in either arm → the finding is about what agents miss that CI
> doesn't catch.**

F4 appears in three runs and F5 in four, across both arms. So this is not a video about
which model is better. It is a video about defects that every suite reports as green.

## What was identical in all six

Migration, schema, model annotation, **1 of 4** parameter entry points, **1 of 3**
serializers, **0 of 3** public swagger definitions, the current contact form, i18n, two
spec files each. No Vue convention violations anywhere. The acceptance check passed in
all six: the field works end to end every time.

On the core of the task the two models are indistinguishable. They diverge only where
the repository itself has no single answer.

## The three findings

**1. Documentation that silently does not ship.**
`swagger.json` and `swagger/tag_groups/*.json` are generated by `rake swagger:build`.
Three runs edited the source definitions and did not regenerate completely: a3 and b2
rebuilt only `swagger.json`; b3 edited four source files and regenerated **nothing**.
The API documentation that is actually served does not contain the change. No suite
catches this — the sources look edited and everything is green.

**2. The linter was switched off rather than satisfied.**
Adding the field pushes `Contact` past `Metrics/ClassLength` — 177 lines against a
limit of 175. Three of three arm-A runs added `app/models/contact.rb` to the exclusion
list in `.rubocop.yml`. All three then reported **zero** lint offences. The number was
true and meaningless. b3 hit the same limit and took the offence instead.

Without the `INSTRUMENT_MODIFIED` guard, added the day before the series, four of six
runs would have shown an identical clean lint result.

**3. Tests asserting behaviour that was never built.**
b3 wrote specs requiring an unsupported language code to be rejected with 422, did not
implement the validation, and shipped with those specs failing. It did not break the
codebase — it broke its own promise, which is worse in one specific way: the next
developer reads the spec and believes the behaviour exists.

## The split that is not noise, and what it is worth

| | validation added | `.rubocop.yml` edited |
|---|---|---|
| Arm A | 3 / 3 | 3 / 3 |
| Arm B | 0 / 3 | 0 / 3 |

Two perfect splits. Arm A added validation for the language code — a1 through the
`iso-639` gem already in the Gemfile, a3 through Chatwoot's own `LANGUAGES_CONFIG`, the
list agents pick interface languages from. All three added the error string to `en.yml`.
Arm B added none.

**At three runs per arm a perfect split carries a two-sided p of 0.10.** That is a
signal worth reporting and not a result worth asserting. It is also not obviously a
point in arm A's favour: the prompt never asked for validation, and `AGENTS.md`
explicitly tells contributors to prefer the smallest production-ready change and to
avoid speculative guards. Arm A exceeded the brief. Whether that is care or scope creep
is a judgement, and it is stated here as one.

## What the frontend actually looked like

**A correction, kept visible rather than edited away.** An earlier version of this
document said that five runs added a plain text input and one added a dropdown. That
was wrong. It came from reading one diff closely and assuming the other five matched,
which is the same mistake this whole benchmark exists to argue against.

All six runs added a searchable `ComboBox`, the same component the country field in that
form already uses. None of them shipped a free-text field.

What differs is where they got the list:

| source | runs |
|---|---|
| `iso6391Languages`, the full ISO 639-1 set | a1 |
| default import of the same languages module | a2, b2 |
| `useConfig().enabledLanguages` — the languages this installation has enabled | a3, b1, b3 |

Three of the six reached for a composable already in scope and offered only the
languages the installation actually runs. That is arguably the more context-aware
choice, and it is split across both arms — two from B, one from A.

So the frontend, like the backend, does not separate the models.

What does separate them is narrower than it first looked: a1 additionally wired the
legacy contact form and added the `LABEL` string, and a1's backend validation is tied
to the full ISO set while the dropdown offers it — consistent. The runs without
validation cannot be reached with an invalid value through the interface either, since
the dropdown constrains input; their exposure is through the API, where a1 returns 422
and they return 200.

> Demonstrated live: a1 rejects `"zzzzz"` with 422 and the ISO 639-1 error string.
> b3 accepts it and stores `'zzzzz'` — while its own spec file contains
> `it 'rejects an unsupported language code'`, failing.

## Limits of the counting

Part A counts which files changed, not what was built inside them. Five of six runs
produced identical A7/A7b rows while sourcing their language list from three different
places.

No automated step distinguished them. Nor, on first reading, did I — I inferred from
one diff. The check that actually settles this kind of question is a human in the
running application, which is why F3d is assigned to a person and not a script.

## Cost per completed task

Taken from provider billing, not from the harness.

| | 3 runs, billed | per completed task |
|---|---|---|
| Arm A | $33.04 | **$11.01** |
| Arm B | $0.20 | **$0.067** |

**164×.**

These are balance deltas bracketing the six measured runs, not console daily totals. They
reconcile: $5.68 for the pilots plus $33.04 for the series is $38.72, which is what the
Anthropic console billed for 2026-09-17. Comparing the daily totals instead gives 73×,
because that day contained one pilot on the expensive side and two on the cheap one.

### Where the expensive money went

The Anthropic console's caching page reports a read ratio of 100% and write amortisation
of 36.1× for the day. That gives an input composition of **97.3% cache reads, 2.7% cache
writes, uncached effectively zero** — 46.6M against 1.3M tokens.

Checked against the bill: 46.61M x $0.50 + 1.29M x $6.25 = $31.38, against $31.29 of
actual input charges once output is removed. 0.3% apart, which also confirms the $0.50
and $6.25 rates rather than assuming them.

Cache writes were **2.7% of input volume and 26% of the input bill**.

DeepSeek's console publishes no equivalent breakdown, so the same decomposition cannot be
done on the cheap side.

That is larger than the per-token ratio, which is 33× on input and 42× on output. The
reason is that the cheaper model did not do less work — context consumed was 27.2M
tokens for arm A against 30.2M for arm B. The price gap is almost entirely rate, not
volume.

A prediction made after the pilots — that the expensive model would be more efficient
per task and so narrow the gap — was wrong. It was based on a single pilot run.

## The absolute cost figures belong to the harness, not the model

The 165× ratio is measured under one harness and both arms sat under it equally, so the
comparison holds. **$11.01 does not.** It is what Opus 5 costs *through opencode* on
this task, and that is not the same thing as what Opus 5 costs.

Same model, same repository, measured here:

| harness | steps | wall | context read |
|---|---|---|---|
| Claude Code | 32–35 | 155–178s | 1.4–1.8M |
| opencode | 48–117 | 702–1513s | 2.5–12.9M |

Four to eight times the wall clock, two to seven times the context, for the same model
doing the same feature in the same codebase.

The comparison is not clean: the Claude Code runs were on the earlier backend-only
prompt, the opencode runs on the full one including the UI. But the UI portion is about
ten lines across four files. It does not account for a sevenfold difference in context.

So: the ratio between the two models is a finding. The absolute dollar figure is a
property of the harness as much as of the model, and quoting it without that
qualification would be exactly the kind of number this project set out to criticise.

Fixing the harness and varying it instead — same model, different tooling — is a
separate experiment. The infrastructure for it already exists.

## What this does not support

- One task. `preferred_language` on one model in one Rails codebase. Nothing here
  generalises to "coding" or even to this repository.
- Three runs per arm, cut from five for budget. See RUBRIC.md § Amendments.
- Reasoning effort could not be pinned; both arms ran at opencode's defaults.
- Model routing was not fully pinned — billing shows a small model being called that
  was never requested.
